> هذه الوثيقة تحكم **التعاون بين المساعدين الآليين** العاملين على منصة FWMS.
> كل مساعد يقرأها قبل أول جلسة عمل، ويلتزم بها بلا استثناء.

---

## 2. مبدأ التنسيق الجوهري

> **المستودع الواحد هو مساحة التنسيق الوحيدة.** لا تنسيق خارج الملفات. كل ما يُتخذ من قرار أو يُنجز من عمل **يجب أن يظهر في الملفات المشتركة** حتى يجده الطرف الآخر في جلسته التالية.

الملفات المشتركة الأربعة (append-only):

1. **`KNOWLEDGE_BASE.md`** — المعرفة: قرارات، اصطلاحات، دروس، أسئلة مفتوحة.
2. **`CHANGELOG.md`** — التغييرات لكل إصدار/دفعة.
3. **`docs/WORKLOG.md`** — سجل الجلسات (قيد لكل جلسة عمل، الأحدث أولًا).
4. **`AGENTS.md`** — الحوكمة (لا يُعدَّل إلا بقرار موثَّق من صاحب المشروع).

## 4. دورة جلسة العمل القياسية (لكل مساعد)

```
1. git pull origin main
2. قراءة: KNOWLEDGE_BASE.md → CHANGELOG.md → قيدَي WORKLOG الأخيرين
3. إن كانت هناك «طلبات موجهة إليك» في WORKLOG → نفّذها أولًا
4. اعمل مباشرة على main (لا تنشئ أي فرع — القاعدة الصارمة §5)
5. نفّذ المهمة + اختبارها (lint إلزامي)
6. حدّث: CHANGELOG (Unreleased) + WORKLOG (قيد جلستك) + KNOWLEDGE_BASE (إن تعلمت/قررت شيئًا)
7. git add → commit (Conventional) → push مباشرة إلى main (بوابة الجودة pre-push نافذة)
```

## 5. قواعد Git

> **قاعدة الفرع الواحد (قرار المالك النافذ 2026-10-19 — أصلًا يُلغي ما تعارض معها):**
> المستودع يملك **فرعًا واحدًا فقط: `main`**. يُحظر على أي مساعد إنشاء أي فرع آخر
> (`feat/...` أو `fix/...` أو `docs/...` أو أي اسم آخر) لأي سبب كان — بما في ذلك
> «العمل دون اتصال» أو «تجربة تغيير كبير». كل الالتزامات تُدفع **مباشرة إلى `main`**.
> إن وُجد فرع جانبي في المستودع: يُدمج في `main` إن كان يحمل عملًا فريدًا، ثم
> **يُحذف فورًا** — والتوثيق في WORKLOG. لا استثناء إلا بأمر صريح موثّق من صاحب المشروع.

- **لا force-push إلى `main`** أبدًا، من أي طرف (خطاف pre-push يرفضه آليًا).
- Commits بصيغة Conventional Commits مع رقم مرجعي عند ربطه بطلب: `feat(api): attendance endpoint (#W12)`.
- أي تعارض دمج: **الطرف الأحدث تاريخًا يتنازل ويُعيد الدمج يدويًا**، ويوثّق ذلك في WORKLOG.
- علامات (tags): `v0.1.0`، `v0.2.0`... عند إتمام كل مرحلة (SPEC §8).

## 6. قنوات طلب العمل المتبادل

في نهاية كل قيد جلسة في `docs/WORKLOG.md`، أضف إن وُجد:

```markdown
### طلبات موجهة للمساعد الآخر
- [ ] <طلب محدد وقابل للتنفيذ> — الأولوية: عالية|متوسطة|منخفضة — السبب: ...
```

مثال من هذه الجلسة (انظر قيد 2026-10-16): المساعد الأول يطلب من الثاني تجهيز `pay_rules` seeds وتشغيل الخادم المحلي.

## 7. التعامل مع الأسرار

- `.env` **لا يُرفع إلى git** (متجاهَل). كل سر يُمرَّر يدويًا من صاحب المشروع إلى بيئة الطرف المعني.
- التوكنات (GitHub PAT / Cloudflare API / Vercel): في `.env` أو أسرار المنصة فقط.
- عند تسريب سر في ملف مرفوع: إبطال فوري + تنظيف تاريخ Git + إبلاغ صاحب المشروع في WORKLOG **فورًا**.

## 8. التعامل مع الأعطال بين الطرفين

| العطل | الإجراء |
|---|---|
| فشل دفع التطبيق للخادم المحلي بعد تغيير المخطط | المساعد الثاني يوثّق خطأ Prisma في WORKLOG؛ الأول يصحّح ويجيب في نفس الملف |
| اختلاف نتائج الأجور بين البيئتين | تجميد الاعتماد، مقارنة `pay_rules` بالفعالية الزمنية، توثيق الفرق |
| فقدان اتصال GitHub | الالتزام (commit) محليًا على `main` دون push، والدفع فور عودة الاتصال (لا إعادة كتابة تاريخ، ولا إنشاء فروع — القاعدة §5) |

## 9. اجتهادات ممنوعة

- ❌ **إنشاء أي فرع خارج `main`** — أياً كان اسمه أو سببه (قرار المالك 2026-10-19، تفصيلها §5).
- ❌ تعديل `docs/SPEC.md` (مواصفة المنتج) من أي مساعد دون أمر صريح من صاحب المشروع.
- ❌ ادعاء إنجاز مرحلة دون اختبار موثَّق.
- ❌ تخطي تحديث CHANGELOG/WORKLOG في أي push.
- ❌ كتابة أي رقم أجر/نسبة مغربية في الكود بدل جدول `pay_rules`.
